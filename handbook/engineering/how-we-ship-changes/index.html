How we ship changes

Reading time4 min
Updated2026-10-14
AuthorsGGeserd team

Every change you can see or feel is written down in the public changelog. Shipping is a habit, not an event.

Before anything goes out

A page is not finished when it looks right on one screen. Before a change ships we look at it on a phone-width and a desktop-width screen, in the dark and the light theme, and in more than one language. We run automated checks that find text left untranslated, layout that overflows sideways, and style names that collide with existing ones. If a check fails, the change waits.

The path of a change

  • Write it. The change and the reason go into the project notes before the code.
  • Build it small. One change at a time, so that if something is wrong we know which one.
  • Test it. The API has automated tests; pages are checked in the browser at real sizes.
  • Update the server. One command pulls the site, another the API, and the service restarts only when it must.
  • Record it. A dated line in the changelog tells you what changed, in all four languages.

Releasing without drama

We prefer many small releases to one large one. A small release is easy to explain, easy to check and easy to take back. When a change touches how mail is sent, we treat it more carefully than a change to a page, because a mistake there reaches your customers rather than just your screen.
