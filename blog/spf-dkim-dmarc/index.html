SPF, DKIM and DMARC, explained without the acronyms

Three records stand between your email and the spam folder. Here is what each one actually does, in plain language.

SPF: who is allowed to send

SPF, or Sender Policy Framework, is a DNS record that lists which servers are allowed to send email for your domain. When a receiving server gets a message claiming to be from yourdomain.com, it checks the SPF record for that domain and compares it against the server that actually sent the message. If the sending server is not on the list, the message looks suspicious, even if nothing else is wrong with it.

An SPF record for geserd looks like v=spf1 ip4:203.0.113.10 ~all, meaning mail can come from that one IP address, and anything else should be treated with a soft fail rather than rejected outright. You only need one SPF record per domain, and if you already send mail from another provider, geserd's IP needs to be added to the existing record rather than replacing it.

DKIM: proof the message was not altered

DKIM, or DomainKeys Identified Mail, adds a digital signature to every message using a private key that only the sending server holds. The receiving server looks up the matching public key in your DNS and checks that the signature still matches the message. If even a single character changed in transit, the signature breaks and the check fails.

This is why geserd generates a separate 2048-bit key pair for every domain you verify: the private key signs your outgoing mail, and the public key is published as a TXT record so any receiving server can verify it. You never handle the private key yourself, and it is encrypted at rest on our side, so a signature can only ever be produced by geserd sending on your behalf.

DMARC: what to do when a check fails

SPF and DKIM can each fail independently without anyone being told. DMARC ties them together: it tells receiving servers what to do when a message claiming to be from your domain fails SPF, DKIM, or both, and it gives you an address to receive reports about it. A DMARC record with p=none asks servers to do nothing special yet, just report; p=quarantine asks them to send failing mail to spam; p=reject asks them to refuse it outright.

We recommend starting with p=none so you can watch the reports for a few weeks and confirm every legitimate sending source, including geserd, passes cleanly, before moving to quarantine and eventually reject. Tightening DMARC too early, before your setup is fully correct, is the most common way real customer email quietly disappears.
